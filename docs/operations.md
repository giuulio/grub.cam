# Operations

[AGENTS.md](../AGENTS.md) lists commands and data rules. [README](../README.md#switching-on-sending-in) is the canonical setup guide for Google sign-in, model secrets and publishing. Google sign-in has been on since 12 Oct 2026.

## Ingest and reference data

`scripts/ingest/sources.ts` records one source per venue: channel, URL, cadence, notes and adapter when scripted. Channels are html/json/pdf/sway/canva/app/email/intranet/none. Ingest copies channel, URL and scripted status to `venues.menu_channel/menu_url/menu_scripted` for Contribute; edit these in the source registry, not the dashboard.

Save every available published menu, no matter how far into the future. The scripted sources cover 20 colleges (11 through adapters, 9 through [documents](#documents)), a separate Magdalene Formal Hall adapter using the same viewthe.menu page as Ramsay Hall, and three University Catering weekly pages through `ucs.ts`. Ingest starts at this week's Monday, or the week containing `--from`, and discovers weeks until the first empty future week, with no fixed lookahead cap. Every published date returned by an adapter is saved, including dates beyond an empty discovery week; repeated whole-source responses replace rather than duplicate dishes. Past empty weeks do not stop backfilling. Jesus, Corpus, Selwyn and Robinson retain historical days. Already saved days remain; a day still listed is saved again only when it differs from the saved one (`menu_days.content_hash`, `dayHash()`; `--rewrite` saves them all). A source returning nothing when it previously had menus saved in the dates it was asked for counts as a failure. The browser's seven-day initial load is only a loading window; later menus are stored and available through the calendar.

`.github/workflows/ingest.yml` is started every half hour from 06:07 to 19:37 UTC by pg_cron (`0042`), covering 07:00–19:30 in London all year, so a cancelled meal or a swapped dish shows up within half an hour. Each run asks every source for as little as covers what can change (`scripts/ingest/lib/checks.ts`, `source_checks`): its first run of the day sweeps every published week (`all`), one every four hours fetches today to the end of next week (`fortnight`), and the rest only today and tomorrow (`soon`). Sources that serve one page for everything cost a request whatever the scope; Jesus's soon check is 4 requests where a sweep is about 100. Sources run at once, one request at a time per host 0.7 s apart; each request times out at 30 s and a network error, timeout, 5xx or 429 is tried once more; each source has a budget (3, 4 or 8 minutes) and the job 20 minutes. A page asked for twice in a run is fetched once.

After a failure a source is tried again at the next run; after two in a row it waits an hour, then two, four and at most six (`retryAt()`). From the second failure in a row it is listed in the **Source health** issue, which also gets a comment (which emails you) when a source starts failing or recovers, and that run fails; a single failure doesn't. Saved menus stay up meanwhile. The Action approves trusted contributor submissions and calls `CF_DEPLOY_HOOK` only when the ingest or those approvals saved something, even if a source failed. Required repository secrets are `VITE_SUPABASE_URL` and `SUPABASE_SECRET_KEY`; the deploy hook is optional.

Hand-transcribed sources use the same validated formats as submissions. Save text outside the repo, conventionally under `~/grub-data/menus/`, and run `ingest:manual`, `ingest:prices` or `ingest:hours`. Format documentation lives at the top of each script. Allergens printed with a dish go in brackets after it, as printed: `Salmon pasta bake (gluten, fish, milk)`, `(may contain: nuts)`; the model is asked for the same, from documents and members' photos. `--dry` validates without writes. Reference data is edited in Supabase until an editor UI exists; schema changes are migrations.

An explicitly cancelled meal is a dated menu note with no dishes: `2026-10-13 dinner | No dinner – UG freshers formal hall`. `ingest:manual` also recognises that notice on its own line. It preserves the cancellation and rejects contradictory dishes. A meal served with its menu posted elsewhere is a note with no dishes too: `2026-10-16 dinner | European Night, see posters for details`. It stays served, and a member's photo of the poster replaces it. A blank meal with no note is omitted. Cancellations remove that date's service from opening status without changing the usual weekly hours. A disruption that day is an alert: start the note with `!` (`2026-10-13 lunch | ! Served at the top table after a leak; dishes may change`) and it shows in red instead of as a quiet note (`menu_days.alert`, migration `0035`). Give times in it only if they change that meal's hours. Trinity's public weekly PDFs can retain removed text behind blank meals and cancellation notices: transcribe the rendered page, not the extracted text alone.

Member text and confirmed transcriptions accept up to 20,000 characters. Longer input is rejected with an error rather than silently cut; this also prevents a pasted weekly menu from losing its final day.

Fixed menu items can include a description or choices in the price format's optional fifth field: `Shakshuka | £7.15 | | | Tomato sauce, poached eggs and feta`. This is stored in `venue_prices.description` and displayed beneath the item name. Keep ingredients out of the name when they are printed as a separate description; preserve the source's choices and infer no dietary tags.

Source quirks worth preserving:

- PDFs: `curl -A "Mozilla/5.0" … | pdftotext -layout - -` extracts layout. Sway/Canva can be inspected with headless Chrome's `--dump-dom`.
- Canva's rendered DOM shows only the first page; later text is in JSON `"A":["…"]` runs, with supper blocks before their day labels.
- Lucy Cavendish uses V = vegan and Vn = vegetarian; transcribe explicit `(vegan)` / `(vegetarian)`. Clare Hall's PB means plant-based. Never assume a diet code's meaning.
- St Catharine's PDFs contain the whole four-week cycle and each week's dates. Fitzwilliam and Lucy Cavendish also publish formal menus; save them at service `formal` on the room that holds them.
- Queens' page has a BotDetect CAPTCHA, including in headless Chrome. Members-only sources need a collaborator.
- Magdalene can fail locally because of keychain cross-signed certificates; retry with `NODE_USE_SYSTEM_CA=0`.
- Jesus and Corpus run the same menu app, whose College pages offer dates up to eight weeks ahead. Since 12 Oct 2026 Jesus's endpoint answers any date with a menu (checked into 2035), so both adapters stop at today + 56 days; otherwise discovery never finds an empty week.
- Pembroke's servery page dates every week of its three-week cycle and links each week's PDF once posted: save each PDF for every week it lists.

### Documents

Nine colleges publish their menus as documents rather than data: Fitzwilliam, Trinity, St Edmund's, Pembroke and St Catharine's as PDFs, Clare Hall as a Microsoft Sway, Lucy Cavendish as a Canva design, Churchill and Newnham as pages. Their sources in `sources.ts` have `documents` (`scripts/ingest/sources/<college>.ts`), and six University cafés' price lists have `prices`. `scripts/ingest/lib/docs.ts` runs them, keeping each document in `source_documents` (`0043`):

- **Fetched only when it may have changed.** Each run fetches the source's listing page (one request); a PDF is asked for with its last ETag/Last-Modified (a 304 costs nothing), and Trinity's, whose links carry a token, only when its upload stamp (`ind`) changes. Sway and Canva are drawn by headless Chrome (`lib/browser.ts`; the runner's `google-chrome`, or `CHROME_PATH`) and hashed on their menu's text alone (`between()`), not the cookie notice or the viewer's buttons.
- **Read only when its content changed.** Churchill and Newnham have parsers; the rest, or a parser that throws, are read by the model (`lib/model.ts`): the submit function's prompt and answer shape (`_shared/`), with each source's `guide` (its codes, its cancellations, which week a cycle PDF is), then `parseManual()` and `checkDays()` (dates within the document's week or a plausible range, no meal without dishes unless cancelled). About 2 cents a document on `gpt-6.1-sol`; on 13 Oct 2026 the model's readings matched the hand transcriptions dish for dish except where they had corrected the college's spelling. `--reread` reads every document again.
- **Cycles.** Pembroke's page dates each week of its three-week cycle: a week's PDF is read once, dated as its first week, and copied to the others (`expandWeeks()`). St Catharine's PDFs date themselves ("(12.10/09.11)") and are read once a term. St Edmund's week is its post's.
- **A person's day stays** until the document changes after they saved it (`docChanges()`): a document first seen never replaces a hand-transcribed or member's day, and neither does one whose hash changed only because our code did (the hash records the code that cut and read it, `schemeOf()`), or whose new reading is the same menus. To put a hand transcription back over a model's reading, save it again with `ingest:manual` (with no `fetched:` line, it's saved as of now).
- **Not readable** (the model found no menu, wouldn't vouch for it, or a date outside its week): the document is kept as `failed`, listed in the Source health issue with a comment, and not sent to the model again until it changes or `--reread`. Without `OPENAI_API_KEY` a document waits instead (not marked failed) and is read once there's a key.
- **Price lists** are checked on the venue's first run of the day. A document first seen while the venue lists prices from it is taken as what the site lists; once it changes, the model's reading replaces the lines whose source is that document (others, such as the Cavendish Café's member photos, stay), refused when it has a price over £100, unnamed columns, or fewer than half the lines it had.
- **Adapters with `fallback`** (Darwin, Robinson, Selwyn, St John's, Wolfson and University Catering): when the adapter breaks on its page (not when the page can't be fetched), the model reads the page's text instead, once per version of it; the source still counts as failing, so the adapter gets fixed.

Lucy Cavendish's Canva is read fine from a home connection, but Canva puts a bot check ("Just a moment… Verification") in front of GitHub's runners: the scheduled run reports it in Source health rather than getting round it, so read it with `npm run ingest -- --only lucy-cavendish` from your machine, or transcribe it. Queens' is public but behind a CAPTCHA (its page redirects scripts to SiteGround's `sgcaptcha`), also in headless Chrome: it stays hand-transcribed, never got round.

## Submissions

There are several publication routes: scripted public sources; hand-entered data; trusted contributors' scripts; members' menus, price lists and hours the model is confident of; vetted venue and site photos; and checked reviews. Corrections and anything held back wait for a person. `AUTO_KINDS` (function secret, default `menu,prices,hours`) says which kinds go up without one; `menu` alone makes prices and hours wait again.

`/send?venue=<id>&kind=menu|prices|hours|photo|other[&topic=…]` links from venue gaps, Contribute and the footer. A correction (`other`, “Report a change”) picks a `topic` (hours, prices, menu, formal, diet, location, closed, other; `0031`), which gap links fill in and the queue shows. Nothing limits how much an account sends; the hashed IP is kept, not limited, since a college's Wi-Fi can be one address. A board can take up to ten photos or PDFs (a week's menu on several sheets, a college's PDF), read together in one call; a venue photo is one photo. They come from the camera or the library (the page offers both: `capture` alone forced the camera on phones), are dropped or pasted on a computer, and `src/lib/submit.ts` shrinks each photo to 1600px; PDFs (10 MB at most, `0038`) go as they are and reach the model as files. The bucket holds them as `<id>.jpg`, `<id>-2.pdf`, …; `submissions.photo_paths` lists them in order and `photo_path` stays the first (`0037`). A note sent with them is context the model reads (“next week's menu”, “top half is lunch”). The submit function validates a member's bearer token through Auth and requires `@cam.ac.uk`, stores evidence in the private `submissions` bucket and creates a row (`0024`, member identity in `0026`). Contributor-token posts have their own validation. Uploaded board/list photos are private evidence, not public photos.

For menus, price lists and hours, the Responses API produces the ingest text body, whether anything was readable, any uncertainty, and a verdict: `publish` when it clearly is what was asked for and every date, meal, item and price is read rather than guessed, else `retry` with one sentence telling the sender what to send instead (a blurred or cut-off photo, the wrong venue's menu, a board that doesn't say which half is lunch). The page sends one request (`auto=1`, `stream=1`), and the sender watches the reading arrive: the function answers in `application/x-ndjson`, a `text` event with the body so far (read out of the partial JSON by `partialString()`), then `done`. On `publish` the row is checked like a confirmation (`holdOf()`: `AUTO_KINDS`, the sender's day, a scripted venue's menu) and queued, or left `needs_review` with that reason; on `retry` it is `rejected` with the model's reason, which the page shows over the form, files kept, to try again. A menu's days and meals come from the board (`as_board=1`): the model is told today's date and this week's dates, and the date and meal sent (now's, by the venue's hours) apply only where the board says neither. With no model to read it, a row stays `received` for a person. Without `auto=1` the function returns the reading for the sender to confirm (action `confirm`), as the page did before 13 Oct 2026; a reading unconfirmed after a day moves to `needs_review` by pg_cron's hourly `hand_over_unconfirmed()`.

### Member menus

`menuWait()` (the function) queues a member's menu when no script fetches the venue's menu. `.github/workflows/photos.yml` runs `submissions -- publish`; `menuHold()` checks that it parses, contains dishes, belongs to that venue, is dated yesterday or later in London dates (no future cutoff), and is still not scripted. Failures move to `needs_review` with a reason; passing menus are saved through the manual-menu parser. Historical submissions can still be checked and approved manually.

Rejecting a published member menu removes its days where they still belong to the member-ingest method; a script's or hand-copied menu for those days stays. The same rejection path can remove a contributor's published menu.

### Member price lists and hours

The model reading a price list or hours is given the venue's current list (`currentText()`). Hours come back whole: a photo of part of a board or a typed change (“Monday closes at 2”) returns the whole list, with the change made. A price list comes back as what was sent alone, under the board's headings; a typed correction (“the latte is now £3”) as the whole section it changes. On confirmation, `holdOf()` queues it unless they changed the reading of a photo and `checkReading()` (the check model, purpose `check_reading`) can't find every line on the photo or in the earlier list. `submissions -- publish` (the photos Action) then checks it parses, is for its venue and has no price over £100, keeps the rows it replaces in `submissions.replaced` (`0032`), and saves it. `reject <id>` on published hours puts those rows back, unless the venue's hours have been replaced again since.

A member's price list is merged into the venue's by section when it's published (`mergeList()`, `0041`): its sections replace the ones under the same headings (in any case; lines under no heading are one section), where they were; the venue's other sections stay; new ones follow. Each line keeps its own `source` and `observed_on`, so the page credits everyone whose sections it shows. The merge happens at publication, one submission at a time, not when the model reads: on 13 October 2026 Café Lucy's specials board, sent a minute after its drinks menu and read before the drinks went up, replaced them. `reject <id>` puts back the sections it replaced that are still all its own, and takes out the ones it added; a list published before `0041` puts back the whole list before it while all of the venue's list is still its own. A section a venue drops from its board stays until someone removes it: `ingest:prices` still replaces the whole list.

A board with two prices a line comes back with a `columns:` line naming each as the board heads it (`columns: Full price | SFC rate`; a column headed only “£” is the full price), saved as `venues.price_terms.tiers`; `currentText()` passes the venue's names back to the model. A list with two prices a line that names neither column, for a venue whose columns aren't named either, waits for a person (`unnamedColumns()`): the page would otherwise guess “Members, Others”, which put Pembroke's full price over the students' rate. Approval and `ingest:prices` refuse it too. Sizes are separate items, never columns: a `columns:` line naming sizes (“Single | Double”, as The Buttery's espresso was read) is held the same way. When a list renames the columns, the venue's terms before are kept in `submissions.replaced_terms` (`0036`) and `reject` puts them back unless they've been renamed since.

### Venue and site photos

A member grants CC BY 4.0 and is credited using their Google account's name (`memberName()`). A photo is of a venue (`/send?venue=…&kind=photo`, from its banner) or of a college or University site itself, for its page's banner (`/send?site=…&kind=photo`, from the site's banner): the submission then has `site` and no `venue_id` (`0040`), and only a photo can. `vet()` checks that the image is a real photo of the venue (or of the college or site: its buildings, courts, grounds, or a hall or café in it), has no recognisable face or unsuitable content, and supplies alt text. It is queued automatically unless another member's photo of the same venue or site was queued or approved in the preceding 24 hours; the sender's own don't count, so one member can send several. Failed checks or unavailable models send the photo to `needs_review`.

The submit function starts the publishing workflow for a queued menu or photo through `dispatch_workflow()` (migration 0031, the GitHub token in Vault as `github_dispatch_token`); pg_cron's hourly 23-past start catches missed dispatches. `submissions -- photos` writes image variants to `public/photos` and adds an unapproved row ahead of the venue's (or site's) older photos. The Action commits the files to main, which starts a deploy. `submissions -- live --wait 720` approves rows only when the site serves their files; otherwise the next run checks again. This preserves the old photo during deployment. Manual approval follows the same path; when approving locally, commit the generated files and run `live` after deployment. Rejecting a photo unapproves it so the previous one can show.

### Names and the leaderboard

Every member submission stores `credit` when it's sent: the name the Google account gives, else the CRSid (`senderOf()`; the form says "Goes up as …"). Once approved it is public through two views (`0039`): `contributions` (approved, named, member submissions: kind, venue, dates, name and an md5 of the account id, for `/contribute`'s leaderboard and "Just added") and `venue_credits` (who sent the price list, hours and each menu day a venue shows now, found through `venue_prices.source`, `service_slots.prov.submission` and `menu_days.source_url`, all "submission <id>…"). Rejecting a submission takes its name off both. The first members' earlier submissions were named on 13 October 2026, with their agreement, from their accounts' names. Points are worked out in the browser (`src/lib/contributors.ts`), not stored.

### Review queue and manual approval

`submissions -- list` lists waiting rows; `show <id>` downloads evidence under `~/grub-data/submissions/` and prints the transcription/prompt. When APIs are unavailable, use the prompt from `_shared/formats.ts` with the photo, save the checked text, then `transcribe <id> file.txt` and `approve <id>`.

Approval validates through `parseManual`, `parsePrices` or `parseHours`, using the same database calls as hand ingest (`method: user`, or `contributor`). Menus upsert days; prices replace the sections they list; hours replace slots unless `--keep-hours` is passed; either keeps what it replaced for `reject`. Slot provenance records the submission. Notes (`kind: other`) require acting on the note rather than publishing it with `approve`.

The queue Action (`.github/workflows/queue.yml`) keeps one open “Review queue” issue. Every newly inserted submission starts it through the database (`0033`), including contributor submissions and anything published automatically. `submissions -- notify <issue>` adds one receipt comment per submission, with only its kind, correction topic, venue link and private CLI command. It never copies submitted words, photos, model output or sender details. Subscribe to the issue for GitHub notifications; email delivery follows your GitHub notification settings.

`submissions.notified_at` records successful delivery independently of publication status. A bot comment's submission marker prevents a duplicate if GitHub accepted it but the database acknowledgement failed. Runs are serialised; pg_cron retries outstanding receipts every ten minutes. Existing submissions were marked as the baseline when `0033` was applied, so enabling this does not announce old submissions.

pg_cron also starts the Action at 07:00 and 18:00 UTC. `submissions -- digest` includes kind, venue, age, reason, action commands, held-back review counts and model spend. It excludes personal details, evidence and review words because the repo is public. Review-queue changes trigger a summary comment; spend-only changes do not.

### Contributors and limits

Contributors post their own complete ingest-format transcription with `X-Contributor-Token`. `contributors` stores a SHA-256 token hash, active status and optional allowed sites. Generate 32 random bytes as hex, save `encode(sha256(token), 'hex')`, and give the contributor the raw token. Rows wait as `needs_review`; the ingest Action runs `approve --trusted` and publishes them as method `contributor`. See [CONTRIBUTING.md](../CONTRIBUTING.md) for the HTTP format.

Each member submission accepts up to ten photos or PDFs for a board (one photo for a venue), each at most 5 MB a photo or 10 MB a PDF. There is no cap on how much one account sends, per hour or per day, and none on how much of it goes up without review: early on a few members fill in whole sites at once. A venue photo waits for review only if another member's photo of that venue was queued or published in the preceding 24 hours; the sender's own earlier photos don't count. The function has a honeypot and keeps a salted IP hash for investigation, without limiting a college's shared IP. Review writes have a separate limit. `IP_SALT` is an optional secret used for the hash.

## Models and spending

Secrets are set with `supabase secrets set`; deploy the function with `supabase functions deploy submit`. To try a change to it before it replaces the live one, deploy a copy (copy the folder to `supabase/functions/submit-next`, `supabase functions deploy submit-next --no-verify-jwt`, delete the folder) and set `VITE_SUBMIT_FUNCTION=submit-next` in `.env.development.local`; `npm run dev` then sends there. Delete the copy (`supabase functions delete submit-next`) and the line once `submit` is deployed. The implementation and price table live in `_shared/openai.ts`:

| Secret | Purpose/default |
|---|---|
| `OPENAI_API_KEY` | Required for transcription and photo/review checks |
| `OPENAI_MODEL` | Boards, price lists, hours; `gpt-6.1-sol` |
| `OPENAI_CHECK_MODEL` | Venue photo/review checks; `gpt-6-luna` |
| `OPENAI_PRICE`, `OPENAI_CHECK_PRICE` | Override dollars per million input/output tokens, e.g. `2/10`; required for cost accounting when the model is absent from `priceOf()` |
| `OPENAI_REASONING` | Optional reasoning effort for both models |
| `LLM_DAILY_USD` | Optional application daily spend check; unset means unlimited |

Model defaults are implementation choices, not a measured board-accuracy result. Compare on real board photos beside hand-checked `.txt` transcriptions with `npm run models:compare -- <dir> --model gpt-6.1-sol --model gpt-6-luna`. It scores lines and reports cost and time. Per-board cost depends on the image and output; do not treat it as a fixed price.

Successful model responses are logged in `model_calls` (`0029`) with purpose, model, token usage, cost and whether the answer was useful. The application has no monthly cap. To stop calls at a monthly amount, configure the OpenAI project's spend limit and enable **Enforce a hard limit**; an alert threshold alone allows traffic to continue. Enforcement can lag slightly. See [OpenAI's spend-limit guide](https://developers.openai.com/api/docs/guides/spend-limits).

`LLM_DAILY_USD` checks logged spend before a call; it is not a reservation and concurrent/in-flight calls can exceed it. When a key is absent, a spending check stops a call or the API fails, transcriptions and checks fall back to the human queue. Rating-only reviews need no model. Review words also use `omni-moderation-latest`, so allow that model if the OpenAI project restricts model usage.

## Reviews

Migration `0030` provides one review per member/venue, with a 1–5 rating and optional text up to 1,000 characters. Writes go through `submit` (`action: review`); members can edit or withdraw their own review. A rating alone is published directly. Words must pass moderation and the check model's test that they concern the venue and name or attack no one; otherwise they wait as `needs_review`. A hidden review stays hidden after author edits. The function limits members to 20 review writes in the preceding 24 hours.

The public `venue_ratings` and `venue_reviews` views show a venue only after five published reviews and expose no author; the threshold cannot be bypassed through the public views. Members read their own reviews through RLS. Ratings load with the initial data (optionally, so missing review tables do not break the site); written reviews load on demand via `useReviews()`.

Use `npm run reviews -- list [--all]`, `approve <id>` or `hide <id> "why"`. The private command prints words and author; the public queue issue does not.

## Photos

`VenueImage` uses the first approved venue photo by position, or the type tile when none exists or loading fails. Site images use their photo or a mortarboard/building tile. Venue photos appear in banners, finder/site rows, credits and `og:image`; site photos appear in their banner, credits and `og:image`. Credits include author, licence deed and source; member banner credit overlays the photo, on a venue's banner and a site's alike, and both banners offer "Have a better photo?".

Files live at `public/photos/<site>/<venue>/<id>-<width>.webp`; site photos use `<site>/<id>`. Variants are 240/480/960/1600px, never upscaled, upright and stripped of metadata. Paths are never reused and are cached immutably (`public/_headers`). `photos` (`0018`, expanded for sites in `0025`) stores subject, path, widths, size, average colour, alt text, credit, licence and source. Only approved rows are readable. `VITE_PHOTOS_URL` can move serving to a separate host; files otherwise use the site's own `/photos`, preserving Supabase's shared free egress.

`ingest:photo` accepts a venue id or site slug and a local file, Commons page URL or `File:Name.jpg`. For Commons it reads author, licence and source, refusing anything outside CC0, public domain, CC BY and CC BY-SA. `--list file` ingests a batch and skips saved entries; `photos-commons.txt` and `photos-sites-commons.txt` record sources. Manual ingest approves the row immediately, so commit/deploy files promptly. Member photos use the staged approval workflow above. Menu-board photos (`kind: menu`) are evidence and are not shown.

## Accounts

For current status and all setup steps, see [README](../README.md#switching-on-sending-in). Reading needs no account. Members sign in with Google: every member has a CRSid@cam.ac.uk Google Workspace account, and UIS documents this as "Raven OAuth2" for sites outside UIS, registered with an ordinary Google account and no approval. `signIn()` passes `hd: cam.ac.uk` so Google offers that account; `hd` is only a hint, so the database's check is what enforces it. Microsoft (Entra) was dropped on 12 Oct 2026: UIS registers apps for Cambridge's tenant through its Application Factory and an allowlist, so an outside app likely needs their approval, and the maintainer's account could not register apps.

`npm run auth:google` uses the Management API to configure the provider and redirect URLs. `-- --check` reads config only; it does not prove end-to-end sign-in works. `useSignInEnabled()` reads `/auth/v1/settings` and hides sign-in offers until enabled. The account button returns to the page it started from; `SignInError` displays `error_description` under the header.

`submit` has `verify_jwt = false` in `supabase/config.toml` because it validates user bearer tokens through Auth itself and separately supports contributor tokens. Migration `0026` rejects new auth users outside `@cam.ac.uk`; `isCamEmail()` checks on the client too. Regular member sign-in uses Google, not email magic links. The email provider stays on (signups need confirmation, so it gives no way in) because the smoke test signs in through it.

`submissions -- smoke [--venue v] [--photo f.jpg [--site s]] [--review]` checks the deployed function (or `VITE_SUBMIT_FUNCTION`'s, a copy being tried) without Google using an admin-created throwaway account (no email sent). It sends a typed menu and marks it wrong, optionally vets a venue photo (or with `--site`, a site's) then rejects it, and saves/removes a review. It deletes the account, submissions and evidence afterwards; model-call logs remain. It checks the submission API, not Google's OAuth flow or a full publication/deploy cycle.

## Deployment and indexing

Cloudflare Worker `grub-cam` serves static `dist/` through `wrangler.jsonc`, with no script and no SPA fallback. Each route is a real file (`/jesus/caff` → `jesus/caff.html`); `404.html`, `_headers` and `_redirects` control missing pages and static behaviour. Every main push runs `npm run build` then `npx wrangler deploy` through Workers Builds.

Set build variables under Settings → Build → Variables and secrets, not runtime variables: `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, optional `VITE_MAPKIT_TOKEN`, optional `INDEXNOW_KEY`, optional `GITHUB_TOKEN`. The header's star count is read at build time; unsigned, GitHub allows 60 calls an hour per address, which Cloudflare's shared build machines often use up, so the count drops out. `GITHUB_TOKEN` is a fine-grained token with public-repository read access only; a build that can't read the count logs why. The last is 8–128 hex characters (`openssl rand -hex 16`); builds write `/<key>.txt` and submit page URLs to IndexNow. Without it, no IndexNow request is sent. ## Map configuration and new coordinates

MapKit JS tokens are configured in Apple Developer → Services → Maps → Configure → Tokens and set as `VITE_MAPKIT_TOKEN` in build/local environments. Domain-restricted tokens match exactly; list multiple domain tokens comma-separated and `pickToken()` selects one. Local development uses a separate unrestricted token in `.env.development.local`. Missing/refused tokens fall back to OpenFreeMap. Optional `VITE_MAP_LIGHT_STYLE_URL` / `VITE_MAP_DARK_STYLE_URL` override fallback styles; `VITE_MAP_STYLE_URL` supplies an override for either theme without its own override.

For new coordinates, first identify the venue's building from a college/University source. Query the University map's `UoCUniMapBuildingsGroup_View` layer with point-in-polygon (`geometry=lon,lat&spatialRel=esriSpatialRelIntersects`), then store the building's latitude/longitude and its `objectIds=` query URL as the location source. Migrations `0012`, `0013`, `0015`, `0019` record earlier research. An OpenStreetMap building outline can supply the building centroid when absent from the University map, as for Lucy Cavendish's New Building. Do not substitute a site centroid or guess a room location.
