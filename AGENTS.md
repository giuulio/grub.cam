# Grub (grub.cam) — agent notes

Cambridge college and University menus, hours and access, live. Vite + React 19 + TypeScript + Tailwind 4 SPA reading Supabase (Postgres). **The database is the system of record**: sites, venues, hours and menus live there, not in the repo. A site is a college or a University site (West Cambridge, Sidgwick, a museum, …); a venue belongs to one. Those are the only two words for them, in copy, code and URLs: never "place". The repo holds code, migrations, and how each venue publishes its menu.

## Commands

| Command | What |
|---|---|
| `npm run dev` | Vite dev server (needs `VITE_SUPABASE_*` in `.env`) |
| `npm run ingest -- [--only jesus,homerton] [--dry]` | Copy every source's channel to `venues`, then fetch every scripted source from this week's Monday until a week comes back empty → Supabase |
| `npm run ingest:manual -- menu.txt [...] [--dry]` | Save hand-transcribed menus → Supabase (format at the top of `scripts/ingest/manual.ts`) |
| `npm run ingest:prices -- prices.txt [...] [--dry]` | Save a venue's posted price list → Supabase, replacing the last one (format at the top of `scripts/ingest/prices.ts`) |
| `npm run ingest:photo -- <site>/<venue> <photo.jpg \| Commons file> --alt "…" [--credit …] [--kind menu] [--dry]` or `-- --list file` | Make a photo's sizes into `public/photos` and add it to Supabase, credited from Commons (see Photos) |
| `npm run ingest:hours -- hours.txt [...] [--dry] [--keep]` | Save a venue's opening hours → `service_slots`, replacing its slots unless `--keep` (format at the top of `scripts/ingest/hours.ts`) |
| `npm run submissions -- list \| show <id> \| transcribe <id> file.txt \| approve <id> \| approve --trusted \| reject <id> "why"` | The queue of what people sent in from `/send` (see Submissions) |
| `npm test` | Vitest (time logic, filters, search against a real-data snapshot, SEO output, adapters against saved pages) |
| `npm run search:snapshot` | Save what the app loads today to `src/lib/fixtures/snapshot.json` for the search tests (then re-check their dish examples) |
| `npm run typecheck` / `npm run lint` | `tsc -b` + scripts tsconfig / oxlint |
| `npm run build` | typecheck + Vite build + `scripts/prerender.ts` → `dist/` (needs `VITE_SUPABASE_*`: pages are rendered from live data) |

`--dry` fetches and validates without writing. If ingest gets "fetch failed" for Magdalene locally, run with `NODE_USE_SYSTEM_CA=0` (keychain cross-signed certs break that chain).

## Layout

- `scripts/ingest/sources.ts` — **how each venue publishes its menu**: one entry per venue (`venues.id` = `<site>/<venue>`), channel (html/json/pdf/sway/canva/app/email/intranet/none), URL, cadence, notes, and an `adapter` for the 14 scripted ones (`scripts/ingest/sources/*.ts`: 11 colleges, plus `ucs.ts` for the three University Catering pages with a weekly menu). Adapters must take dates from the source, never from the requested week; tests run them on saved pages in `sources/fixtures/`. Each run copies channel, URL and scripted-or-not to `venues.menu_channel/menu_url/menu_scripted` (`0007`), for `/coverage`; edit them in `sources.ts`, not the dashboard.
- `scripts/schema.ts` — zod for `Dish` / `MenuDay`, checked before anything is saved; the app imports the types.
- `supabase/migrations/` — tables + RLS (anon SELECT only). `sites` (`kind` college | university) → `venues` (`url` = the venue's own page) → `service_slots` (meals: breakfast, brunch, lunch, dinner, formal, snacks = café, bar) and `formals` (booking, dress, guests, price notes; one per venue that holds formal hall); `0004` seeded the University venues once, `0009` reviewed the whole list, `0014` checked the University ones against catering.admin.cam.ac.uk/cafes. Menus: `menu_days` (one per venue/date/service, upserted) → `menu_items` (dishes as printed, replaced per day) → `dishes` (one per site + `dish_key(name)`, tracked across weeks); `dish_stats` view; `ingest_runs` (one row per source per run; service role only). Price lists as posted: `venue_prices` (`0008`, `0011`, `0017`, `0020`, `0021`; a first and a second price, replaced per venue; a line can be a range ("£3.24–£3.96", `price_max_gbp`), or priced for the second tier only; a line can price a course or the whole meal at some meals, else it's an item sold at them; diet `tags` from the codes printed after a name). Dishes can carry a second price too (`menu_items.price2_gbp`: Robinson's non-member, Wolfson's others'). Whose the two prices are and how a venue's pricing works is the venue's own convention, kept in `venues.price_terms` (`0020`, edited in the dashboard): `tiers`, the price columns' headings in its order (Members/Non-members, Senior/Student, Students and staff), and `note`, its rule for anyone else in words (St Catharine's: VAT on top, a further 35% for external customers; Wolfson: students 25% off), shown under its menu and list. Never compute a price from a percentage: say the rule. `formals` (`0017`): the fields the page shows (`gowns`, `dress_code`, `guests_allowed`/`guests_max`, `book_via`, `book_days_before` + `book_by`, `url`, `price_gbp`/`guest_gbp`/`prices_seen`, `days` when there's no slot), filled only where the notes say it plainly; the other text columns are notes. `photos` (`0018`, `0025`, see Photos). Writes go through `save_menu()` / `save_prices()` (service role only). Moving a venue to a new id moves its slots, menus, ingest runs, prices, formals and photos.
- `src/lib/data.tsx` — `load()`s sites/venues/slots and the next 7 days of menus (`main.tsx` renders once it has, keeping the prerendered HTML up until then); `useMenuDates`/`useMenuOn` fetch a venue's full menu history (past and future) on demand. `src/lib/time/*` — Europe/London clock, Full Term dates, `openStatus()`; `src/lib/filters.ts` — ranking and sections (Open now / Later today / Other days / Hours not published). `src/lib/seo.ts` — per-page descriptions and schema.org data, sitemap, llms.txt.
- `src/pages/*` — the venue is the unit: `/` map-led Explore (MapLibre GL, loaded in the browser; verified venue/building points from `venues.latitude/longitude/location_source`, `0012`/`0013`/`0015`/`0019`; every venue is its own pin, coloured by type, and opens a panel (`VenuePanel`) as Google Maps does: down the map's left side above a phone, a sheet from the bottom on one, with its photo, status, the dishes that matched and the other venues in its building; the map moves a picked pin clear of it; List is the accessible view including unmapped venues, rows of `VenueCard`, one to a line; one row of controls (search, type chips, Open now, Filters, the Map/List switch); over the map the filters open in the same left-side panel, in the list they open above it, and on a phone over the map; the map fills the rest of the screen with its key and count in a corner (moved beside the panel while it's open), and on a phone a floating button switches Map/List; filters in the URL: `q`, `type` (hall/cafe/bar; `hall` is labelled Dining), `open`, `access`, `diet`, `date` (within the loaded menu week), `site`; with Dining also `meal`; `view=list` and `venue` preserve the view and selection (`place`, the old name, is still read); `src/lib/explore.ts` validates URL state and pins menu matches to the selected date, without previewing tomorrow; Near me requests location only on click and keeps it in memory), `/directory` (every college and University site as a ruled index, one to a line: its photo (`SiteThumb`), its name, types, venues, what's open now and whether there's a menu today; `kind` (college/university), `q`, `sort` (name, open, venues) in the URL; `/colleges` and `/university` redirect to it, in the app and in `public/_redirects`), `/:slug` site, college or University (its venues, dining → cafés → bars; old `#venue-slug` links redirect), `/:site/:venue` venue (one structure for every venue, every part shown even when unknown ("Not known yet", "No menu here yet. Help get it here", "No photo yet. Send one"), so missing information is visible and can later be contributed: its picture as a banner across the top (its photo, credited, or its type's tile); name, site and types (`venueTypes()`, plus Formal hall), the details under them (access, payment: bank card / University card / cash, diet options, map, website, "Report a change"); a right-hand column that stays in view while the page scrolls (as TheFork keeps its booking box) with open now, the hours for the time of year ("In term"/"Out of term"; the other period's when only those are known) and the menu calendar; then a section per type: Dining → Menu, dishes for `?date=` (default today) with prev/next and the calendar of every date with a menu (shown on every Dining page, menus or not; on a phone it opens from the date), meals one under another, a meal served that day with no dishes but its own posted list (St Catharine's breakfast) showing the list as its menu, or its posted list when it has never posted dishes, then Formal hall (first in a Hall used only for formals): when, price, guests, dress, booking; Café and Bar → their posted list, undated, sections in two columns on wide screens; the first section is "Menu", the others are named by type. `priceGroups()` in `src/lib/prices.ts` splits a list between sections by the meals each line is sold at, and puts course prices next to a day's dishes or in the meal's heading, folding the rest under "Deals and extras"; on a phone the hours come first, then the sections, then the details), `/coverage` (colleges, or University sites with `kind=university`: a tile per category with how many have it and a meter, then every site against every category as a grid of squares, full/half/empty for all/some/none of its venues of that kind and a dot where none apply, shape carrying the state so it reads without colour; each square links to what's missing and says it on hover or focus. Categories: menus for the loaded week (Dining venues, not Halls used only for formals: `isFormalOnly()`), dining/café/bar prices (a posted price list or priced dishes), hours, access, card payments; `src/lib/coverage.ts`, also behind the footer count and a venue page's note when it has never had a menu), `/about`, `/terms` (terms of use and privacy: as-is information, allergies, no affiliation, no cookies or analytics, which services see a visitor's IP), `/credits` (every photo with its author and licence), `*` 404. Header: Explore and Directory (active on site and venue pages too), GitHub with its star count (read at build time in `vite.config.ts` as `import.meta.env.VITE_GITHUB_STARS`; null when GitHub can't be reached), theme toggle. Footer: what the site is with the menu count, Browse and Project links, © and the not-affiliated line. Controls share one height (`components/Controls.tsx`: `Segmented`, `Select`, `Chip`, `SearchField`; `.btn`, `.chip`, `.field`, `.icon-btn` in `index.css`). A venue's open status reads the same everywhere (`statusWords()` in `src/lib/status.ts`, drawn by `components/Status.tsx`: "Open" on Light Blue, then "until 16:00"; "Opens tomorrow 08:00"; formal hall is "Formal hall 19:30", never "opens"). ← (`BackButton`) returns to the previous page, else goes up; scroll is kept per history entry (`useScrollMemory`). Every list uses `src/components/VenueCard.tsx` (the venue's photo as a square, or its type's tile until it has one; the site leads in Explore, since many venues share a name). Type: Source Serif 4 for the names of venues and page and section titles (`.title`), Public Sans for everything else, both self-hosted through fontsource so no font service sees a visitor's IP. Colour: the University palette (cam.ac.uk/brand-resources/guidelines/colour) in its approved pairs, tokens in `index.css`: Slate text on white; Cambridge Blue for what's picked (chips, the calendar's date); Light Blue for "Open"; Cambridge Dark Blue for the one main action and focus (Cambridge Blue in dark mode); Warm Blue link underlines (`.link`); dark mode is Dark Blue's hue deepened (`#0d1c21`, panels `#16282f`). Not the University's own typeface or logo: grub.cam isn't affiliated. Avoided on purpose, as the marks of generated UI: pills and 16px-radius bordered cards everywhere (controls are 8px, panels 12px), a hairline border with a wide shadow on the same box (`.raised` is one or the other), boxes inside boxes, indigo, tracked uppercase labels, arrows on buttons. Minimal text, icons from reicon.dev (`reicon-react` via `components/Icon.tsx`; venue types in `lib/icons.ts`: ForkKnife, HotDrink (a cup and saucer; a mug reads as beer), Wineglass2 (a cocktail glass); none on the map); free-text DB fields (`notice`, `hours_text`, `access.text`, …) are research notes for editors and aren't shown.

## Menus

Search (`src/lib/search.ts`, indexed once per loaded snapshot) follows Meilisearch/Typesense/Algolia rather than inventing rules. One document per venue and per dish on a day's menu; a dish carries its venue's names. Fields, best first: venue name (plus "<site> College"), alias, venue type and meals (`dining`/`cafe`/`bar`, `lunch`…), dish name, diet tags and service. Query words match exactly, as English plurals or `SYNONYMS` (spelling variants seen on menus), the last one also as a prefix unless followed by a space; one word written as two or two as one ("stjohns", "dar bar"); stopwords dropped. Typos (Damerau: 1 from 4 letters, 2 from 8, a wrong first letter costs 2) only for a word that matches nothing as typed, so real words never drift ("cake" ≠ "hake"). Words are optional: results are what matches the most of them. Ranking is tie-breaks: typos, worst field, the query naming the whole venue or dish, exact words, then open status. Search sees only what the filters leave: dishes on the selected date (today on Home, never silently tomorrow; browsing still previews the next service), at the selected meal, carrying every selected diet tag. Results bypass opening-status groups. Nicknames are data, not code: `sites.aliases` / `venues.aliases` (`0005`, `0006`), edited in the dashboard. `src/lib/search.test.ts` runs judged queries against a real snapshot (`npm run search:snapshot`) plus rules on made-up data; add a failing query there before changing the rules.

No projected menus: only what a source has published is saved, and sources are re-checked often instead (GitHub Actions runs `npm run ingest` at 05:15, 11:15 and 17:15 UTC; needs repo secrets `VITE_SUPABASE_URL` and `SUPABASE_SECRET_KEY`, then rebuilds the site through `CF_PAGES_DEPLOY_HOOK` when that's set). Days already saved are kept; a day the source still lists is replaced with the latest version. Menus are filed under the meal the venue serves that day when the source names one it doesn't but its brunch counterpart is (Corpus posts Saturday's brunch as "Lunch"): `servedService()` in `src/lib/time/openNow.ts`, applied as menus load.

Hand-transcribed venues (see `sources.ts`): open the URL (PDFs: `curl -A "Mozilla/5.0" … | pdftotext -layout - -`; Sway/Canva: `"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --dump-dom URL`), write a `.txt` outside the repo, `npm run ingest:manual -- file.txt`. Members-only colleges need a collaborator; their photos of noticeboards and price lists go in the same way (menus via `ingest:manual`, prices via `ingest:prices`).

Reference data (hours, access, venues) is edited in the Supabase dashboard until there's an editor UI. Unknown hours ⇒ no slot (UI says "Hours not published", never "closed").

A venue is somewhere you go to eat or drink (`0009`): not common rooms, tea or coffee gatherings, vending machines or overflow seating. Its `type` is what people come to it for (`0017`): Dining (`hall`) serves meals from a menu that changes daily or weekly, so its page leads with the menu for a date; a Café sells a menu that rarely changes, so people look at what's there and what it costs; a Bar is a café for drinks. A University café whose main offer is a hot menu that changes (Scholars Brew, Ground Café, …) is Dining, and keeps its café hours. A café that becomes a bar in the evening, in the same room, is one venue: `type` is its icon, and its café (`snacks`) and bar hours also list it under Cafés and Bars (`venueTypes()`), in filters, search and coverage. Formal hall is the `formal` meal: a slot on the dining venue whose room it's held in, or, where it has a room of its own (St John's, Christ's, Clare, Jesus, Magdalene, Pembroke and Robinson's Hall or Dining Hall, Newnham's Clough Hall, Queens' Old Hall), a dining venue of its own. It's booked ahead, so it only counts towards "open now" when Formal is the meal picked or it's all the venue holds; a `formals` row (`Venue.formal` in the app) lists a venue under Formal even when its days aren't published.

## Deploy

Static `dist/`, every page prerendered: `/jesus/caff` is `jesus/caff.html`, plus `sitemap.xml`, `llms.txt`, `llms-full.txt`, `robots.txt` and `404.html` (no SPA fallback: a missing page is a real 404). Prerendered pages leave out anything that depends on the clock (`snapshot`). Canonical origin `SITE_URL` in `src/lib/site.ts`.

Cloudflare Pages: build `npm run build`, output `dist`, env `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`. Pages are as fresh as the last build: create a deploy hook (Settings → Builds → Deploy hooks) and save it as the repo secret `CF_PAGES_DEPLOY_HOOK` so each ingest run rebuilds. A venue added in the dashboard 404s until the next build.

## Submissions

How information gets in. **Scripted, recurring**: `sources.ts` adapters, run by the ingest Action three times a day (the only automated path). **By hand**: `ingest:manual`, `ingest:prices`, `ingest:hours`, `ingest:photo`, and SQL migrations for reference data, each with its source. **Sent in**: `/send?venue=<id>&kind=menu|prices|hours|photo|other` (`src/pages/Send.tsx`), linked from every gap on a venue page ("Send a photo of the board / the list / the times", "Send one", "Report a change"), the footer and Coverage. The sender adds a photo (shrunk to 1600 px in the browser, `src/lib/submit.ts`) and/or text, no account; the `submit` Edge Function (`supabase/functions/submit`) stores the photo in the private `submissions` bucket, inserts a `submissions` row (`0024`), and has a model transcribe it into the kind's ingest text format — OpenAI first (`OPENAI_API_KEY`, `OPENAI_MODEL`), Gemini if that fails or is unset (`GEMINI_API_KEY`, `GEMINI_MODEL`), never more than `LLM_DAILY_CAP` (25) a day across both, so a burst can't spend the credit; secrets via `supabase secrets set`, deploy via `supabase functions deploy submit`. The sender sees that text, fixes it, and confirms (`action: confirm`), which queues it as `needs_review`; with no model available it waits as `received`. **Nothing is published by the function.** `npm run submissions -- list / show <id>` (saves the photo under `~/grub-data/submissions/` and prints the prompt from `supabase/functions/_shared/formats.ts`, to paste into any chat model when the APIs aren't available) `/ transcribe <id> file.txt / approve <id> / reject <id>`: approve parses the text with `parseManual`/`parsePrices`/`parseHours` and saves it through the same calls as the hand scripts (`method` `user`), replacing the venue's hours (`--keep-hours` adds) and price list, upserting menu days; slots carry `prov.submission`. **Contributors** (`contributors`, a sha256 token hash and optionally the sites they may post for) post JSON with `X-Contributor-Token` and their own transcription from a script that can reach a members-only source; their rows are `needs_review` and the Action's `approve --trusted` publishes them (`method` `contributor`). Mint a token: any 32 random bytes hex, store `encode(sha256(token), 'hex')` in the dashboard, hand over the token. Rate limit: 12 an hour per hashed address; a honeypot field; 5 MB photos. `CONTRIBUTING.md` says this to people. Submission photos are evidence for the transcription, not shown; one worth showing goes through `ingest:photo` with the sender's credit.

## Photos

Every venue has a picture: its photo (`kind` venue, the first by `position`), or its type's tile until it has one or if the photo can't load (the type's tint with its icon in the middle; `VenueImage` in `components/VenuePhoto.tsx`). Every site has one too (`SiteThumb`: its photo, else a plain tile with a mortarboard or a building), in the directory, the credits and as its page's `og:image`; `scripts/ingest/photos-sites-commons.txt` lists them, mostly the lead image of the site's Wikipedia article. It's the venue page's banner, the top of its map panel, its square in lists (with the type's mark in the corner) and its page's `og:image`. Photos of menu boards (`kind` menu) are kept as the source of a transcription and not shown. Each photo is credited where it's shown (author, licence linked to its deed, its Commons page) and all of them on `/credits`.

Files live in the repo, `public/photos/<site>/<venue>/<id>-<width>.webp` (240/480/960/1600 px, never wider than the original, metadata stripped, upright), served by the site itself and cached for good (`public/_headers`; a path is never reused); `VITE_PHOTOS_URL` can move them to a bucket later without touching the database. Not Supabase Storage: its free egress is shared with the database. `photos` (`0018` as `venue_photos`, `0025` for sites: the subject is `venue_id` or `site`, a site's path is `<site>/<id>`) holds each one's path, widths, size, average colour (shown while it loads), alt text, credit, licence and source, and only approved rows are public.

`npm run ingest:photo -- <site>/<venue> <photo.jpg | Commons file> --alt "…"` (or `<site>` alone for the site's own photo) makes the sizes, writes them to `public/photos` and adds the row as approved; commit the files (the site shows the tile until they're deployed). For a Wikimedia Commons file (its page URL or `File:Name.jpg`) the author, licence and page are read from Commons, and anything that isn't CC0, public domain, CC BY or CC BY-SA is refused. `--list file` takes one per line (`scripts/ingest/photos-commons.txt`: every venue's photo from Commons, with what it shows; run again, it skips what's saved). Whose photos: ours, a contributor's with a licence, or openly licensed on Commons (Geograph's are there too), never with recognisable people. Where no free photo of the room exists, the building or court it's in, and the alt text says so. Never from Google Maps, social media or a college's own site: those belong to whoever took them, and Google Maps Platform's terms forbid taking its content out. 39 venues have no free photo yet (mostly in-college bars and cafés, and newer buildings).

## Page alignment

`Container` gives the header, main content and footer the same `max-w-7xl` edges. Lists are always one column (the directory, Explore's list, a site's venues, the credits); only the coverage tiles and a day's meals sit side by side. Prose, hours and menu details keep readable inner widths aligned to the left edge.

## Map

Use verified venue or containing-building coordinates, never a college/site centroid or an invented room location. Unmapped venues stay in the List and the directory. Location sources are recorded in Supabase; `0012`/`0013` seed points from the University map; `0015` adds college venues whose OpenStreetMap point falls inside a University-map building of that college (the building's centroid is stored), or whose building a college source names; `0019` finishes the list the same way (every venue now has a point and a `location_source`), falling back to the OpenStreetMap building outline when the University map lacks the building (Lucy Cavendish's New Building). To locate a new venue: find the building a college page names, `pip` it against the `UoCUniMapBuildingsGroup_View` layer (point-in-polygon query, `geometry=lon,lat&spatialRel=esriSpatialRelIntersects`), store that building's `latitude/longitude` and its `objectIds=` query URL. `src/components/VenueMap.tsx` dynamically imports MapLibre GL (SSR-safe, Vite worker bundled locally) and never groups venues: one marker each, with venues sharing a coordinate set side by side (`sideBySide()` in `src/lib/map.ts`). Pins are dots, no icons, in their type's colour from the Cambridge palette (Dining Dark Crest, Café Warm Blue, Bar Dark Cherry; tokens `--type-*` in `index.css`, validated as categorical colours on both basemaps; Warm Blue replaced Indigo, which read as Tailwind's default), with a white halo: a ring when not open, filled when open now; selection is larger, Cambridge Blue on Dark Blue. The key in the map's corner names the type colours and open/not open; the type chips above carry the same colours with the type icons. It uses OpenFreeMap Bright (light) / Fiord (dark) vector tiles with visible attribution. Styles follow both the theme toggle and system appearance without resetting the camera or selection. Optional `VITE_MAP_LIGHT_STYLE_URL` / `VITE_MAP_DARK_STYLE_URL` override each theme; `VITE_MAP_STYLE_URL` overrides both. On mobile the map fills the viewport below the header edge to edge, with search and filters overlaid; desktop keeps the shared page width and a rounded frame, as tall as the screen allows (`--map-top`, measured by Explore). Wheel/trackpad scrolling and mobile pinch act directly on the map, with rotation disabled; `src/lib/mapGestures.ts` handles desktop Safari GestureEvents on the map canvas only. Page gestures outside the map and keyboard browser zoom are untouched. Default view centres on Cambridge; Show all fits matching points. Zooming out stops at `REACH` in `VenueMap.tsx` (Dry Drayton to Teversham, Histon to Trumpington): the minimum zoom is whatever fits that box at the map's current size, so a phone still sees it all across. Opening status is live, while menu date stays explicit.
