# Grub (grub.cam) — agent notes

Cambridge college and University menus, hours and access, live. Vite + React 19 + TypeScript + Tailwind 4 SPA reading Supabase (Postgres). **The database is the system of record**: sites, venues, hours and menus live there, not in the repo. A site is a college or a University site (West Cambridge, Sidgwick, a museum, …); a venue belongs to one. The repo holds code, migrations, and how each venue publishes its menu.

## Commands

| Command | What |
|---|---|
| `npm run dev` | Vite dev server (needs `VITE_SUPABASE_*` in `.env`) |
| `npm run ingest -- [--only jesus,homerton] [--dry]` | Copy every source's channel to `venues`, then fetch every scripted source from this week's Monday until a week comes back empty → Supabase |
| `npm run ingest:manual -- menu.txt [...] [--dry]` | Save hand-transcribed menus → Supabase (format at the top of `scripts/ingest/manual.ts`) |
| `npm run ingest:prices -- prices.txt [...] [--dry]` | Save a venue's posted price list → Supabase, replacing the last one (format at the top of `scripts/ingest/prices.ts`) |
| `npm run ingest:photo -- <site>/<venue> photo.jpg --alt "…" [--credit …] [--kind menu] [--dry --out dir]` | Make a photo's sizes, upload them to R2 and add it to Supabase (see Photos) |
| `npm test` | Vitest (time logic, filters, search against a real-data snapshot, SEO output, adapters against saved pages) |
| `npm run search:snapshot` | Save what the app loads today to `src/lib/fixtures/snapshot.json` for the search tests (then re-check their dish examples) |
| `npm run typecheck` / `npm run lint` | `tsc -b` + scripts tsconfig / oxlint |
| `npm run build` | typecheck + Vite build + `scripts/prerender.ts` → `dist/` (needs `VITE_SUPABASE_*`: pages are rendered from live data) |

`--dry` fetches and validates without writing. If ingest gets "fetch failed" for Magdalene locally, run with `NODE_USE_SYSTEM_CA=0` (keychain cross-signed certs break that chain).

## Layout

- `scripts/ingest/sources.ts` — **how each venue publishes its menu**: one entry per venue (`venues.id` = `<site>/<venue>`), channel (html/json/pdf/sway/canva/app/email/intranet/none), URL, cadence, notes, and an `adapter` for the 14 scripted ones (`scripts/ingest/sources/*.ts`: 11 colleges, plus `ucs.ts` for the three University Catering pages with a weekly menu). Adapters must take dates from the source, never from the requested week; tests run them on saved pages in `sources/fixtures/`. Each run copies channel, URL and scripted-or-not to `venues.menu_channel/menu_url/menu_scripted` (`0007`), for `/coverage`; edit them in `sources.ts`, not the dashboard.
- `scripts/schema.ts` — zod for `Dish` / `MenuDay`, checked before anything is saved; the app imports the types.
- `supabase/migrations/` — tables + RLS (anon SELECT only). `sites` (`kind` college | university) → `venues` (`url` = the venue's own page) → `service_slots` (meals: breakfast, brunch, lunch, dinner, formal, snacks = café, bar) and `formals` (booking, dress, guests, price notes; one per venue that holds formal hall); `0004` seeded the University venues once, `0009` reviewed the whole list, `0014` checked the University ones against catering.admin.cam.ac.uk/cafes. Menus: `menu_days` (one per venue/date/service, upserted) → `menu_items` (dishes as printed, replaced per day) → `dishes` (one per site + `dish_key(name)`, tracked across weeks); `dish_stats` view; `ingest_runs` (one row per source per run; service role only). Price lists as posted: `venue_prices` (`0008`, `0011`, `0017`; member and non-member prices, replaced per venue; a line can price a course or the whole meal at some meals, else it's an item sold at them; diet `tags` from the codes printed after a name). `formals` (`0017`): the fields the page shows (`gowns`, `dress_code`, `guests_allowed`/`guests_max`, `book_via`, `book_days_before` + `book_by`, `url`, `price_gbp`/`guest_gbp`/`prices_seen`, `days` when there's no slot), filled only where the notes say it plainly; the other text columns are notes. `venue_photos` (`0018`, see Photos). Writes go through `save_menu()` / `save_prices()` (service role only). Moving a venue to a new id moves its slots, menus, ingest runs, prices, formals and photos.
- `src/lib/data.tsx` — `load()`s sites/venues/slots and the next 7 days of menus (`main.tsx` renders once it has, keeping the prerendered HTML up until then); `useMenuDates`/`useMenuOn` fetch a venue's full menu history (past and future) on demand. `src/lib/time/*` — Europe/London clock, Full Term dates, `openStatus()`; `src/lib/filters.ts` — ranking and sections (Open now / Later today / Other days / Hours not published). `src/lib/seo.ts` — per-page descriptions and schema.org data, sitemap, llms.txt.
- `src/pages/*` — the venue is the unit: `/` map-led Explore (MapLibre GL, loaded in the browser; verified venue/building points from `venues.latitude/longitude/location_source`, `0012`/`0013`/`0015`/`0019`; every place is its own pin, coloured and iconed by type, and opens a venue card, with List as the accessible view including unmapped venues; one row of controls (search, type chips, Open now, Filters, the Map/List switch; filters open as a panel over the map), the map fills the rest of the screen with its key and count in a corner, and on a phone a floating button switches Map/List; filters in the URL: `q`, `type` (hall/cafe/bar; `hall` is labelled Dining), `open`, `access`, `diet`, `date` (within the loaded menu week), `site`; with Dining also `meal`; `view=list` and `place` preserve the view and selection; `src/lib/explore.ts` validates URL state and pins menu matches to the selected date, without previewing tomorrow; Near me requests location only on click and keeps it in memory), `/directory` (every college and University site as cards with its types, places, what's open now and whether there's a menu today; `kind` (college/university), `q`, `sort` (name, open, places) in the URL; `/colleges` and `/university` redirect to it, in the app and in `public/_redirects`), `/:slug` site, college or University (its venues, dining → cafés → bars; old `#venue-slug` links redirect), `/:site/:venue` venue (one structure for every venue, every part shown even when unknown ("Not known yet", "No menu here yet. Help get it here"), so missing information is visible and can later be contributed: name, site and types (`venueTypes()`, plus Formal hall); beside it a photo (or "No photo yet"), open now with the hours for the time of year ("In term"/"Out of term"; the other period's when only those are known) and the details (access, payment: bank card / University card / cash, diet options, map, website, "Report a change"); then a section per type: Dining → Menu, dishes for `?date=` (default today) with prev/next and, beside it under the photo, a calendar of every date with a menu (shown on every Dining page, menus or not; on a phone it opens from the date), meals side by side on wide screens, or its posted list when it has never posted dishes, then Formal hall (first in a Hall used only for formals): when, price, guests, dress, booking; Café and Bar → their posted list, undated, sections in two columns on wide screens; the first section is "Menu", the others are named by type. `priceGroups()` in `src/lib/prices.ts` splits a list between sections by the meals each line is sold at, and puts course prices next to a day's dishes or in the meal's heading, folding the rest under "Deals and extras"; on a phone the hours come first, then the sections, then the details), `/coverage` (colleges, or University sites with `kind=university`: a tile per category with how many have it and a meter, then every site against every category as a grid of squares, full/half/empty for all/some/none of its places of that kind and a dot where none apply, shape carrying the state so it reads without colour; each square links to what's missing and says it on hover or focus. Categories: menus for the loaded week (Dining venues, not Halls used only for formals: `isFormalOnly()`), dining/café/bar prices (a posted price list or priced dishes), hours, access, card payments; `src/lib/coverage.ts`, also behind the footer count and a venue page's note when it has never had a menu), `/about`, `/terms` (terms of use and privacy: as-is information, allergies, no affiliation, no cookies or analytics, which services see a visitor's IP), `*` 404. Header: Explore and Directory (active on site and venue pages too), GitHub with its star count (read at build time in `vite.config.ts` as `import.meta.env.VITE_GITHUB_STARS`; null when GitHub can't be reached), theme toggle. Footer: what the site is with the menu count, Browse and Project links, © and the not-affiliated line. Controls share one height (`components/Controls.tsx`: `Segmented`, `Select`). ← (`BackButton`) returns to the previous page, else goes up; scroll is kept per history entry (`useScrollMemory`). Every list uses `src/components/VenueCard.tsx`. White on charcoal (`#1e1e1e`), minimal text, icons from reicon.dev (`reicon-react` via `components/Icon.tsx`; venue types in `lib/icons.ts`: ForkKnife, HotDrink (a cup and saucer; a mug reads as beer), Wineglass2 (a cocktail glass); none on the map); free-text DB fields (`notice`, `hours_text`, `access.text`, …) are research notes for editors and aren't shown.

## Menus

Search (`src/lib/search.ts`, indexed once per loaded snapshot) follows Meilisearch/Typesense/Algolia rather than inventing rules. One document per venue and per dish on a day's menu; a dish carries its place's names. Fields, best first: place name (plus "<site> College"), alias, venue type and meals (`dining`/`cafe`/`bar`, `lunch`…), dish name, diet tags and service. Query words match exactly, as English plurals or `SYNONYMS` (spelling variants seen on menus), the last one also as a prefix unless followed by a space; one word written as two or two as one ("stjohns", "dar bar"); stopwords dropped. Typos (Damerau: 1 from 4 letters, 2 from 8, a wrong first letter costs 2) only for a word that matches nothing as typed, so real words never drift ("cake" ≠ "hake"). Words are optional: results are what matches the most of them. Ranking is tie-breaks: typos, worst field, the query naming the whole place or dish, exact words, then open status. Search sees only what the filters leave: dishes on the selected date (today on Home, never silently tomorrow; browsing still previews the next service), at the selected meal, carrying every selected diet tag. Results bypass opening-status groups. Nicknames are data, not code: `sites.aliases` / `venues.aliases` (`0005`, `0006`), edited in the dashboard. `src/lib/search.test.ts` runs judged queries against a real snapshot (`npm run search:snapshot`) plus rules on made-up data; add a failing query there before changing the rules.

No projected menus: only what a source has published is saved, and sources are re-checked often instead (GitHub Actions runs `npm run ingest` at 05:15, 11:15 and 17:15 UTC; needs repo secrets `VITE_SUPABASE_URL` and `SUPABASE_SECRET_KEY`, then rebuilds the site through `CF_PAGES_DEPLOY_HOOK` when that's set). Days already saved are kept; a day the source still lists is replaced with the latest version. Menus are filed under the meal the venue serves that day when the source names one it doesn't but its brunch counterpart is (Corpus posts Saturday's brunch as "Lunch"): `servedService()` in `src/lib/time/openNow.ts`, applied as menus load.

Hand-transcribed venues (see `sources.ts`): open the URL (PDFs: `curl -A "Mozilla/5.0" … | pdftotext -layout - -`; Sway/Canva: `"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --dump-dom URL`), write a `.txt` outside the repo, `npm run ingest:manual -- file.txt`. Members-only colleges need a collaborator; their photos of noticeboards and price lists go in the same way (menus via `ingest:manual`, prices via `ingest:prices`).

Reference data (hours, access, venues) is edited in the Supabase dashboard until there's an editor UI. Unknown hours ⇒ no slot (UI says "Hours not published", never "closed").

A venue is somewhere you go to eat or drink (`0009`): not common rooms, tea or coffee gatherings, vending machines or overflow seating. Its `type` is what people come to it for (`0017`): Dining (`hall`) serves meals from a menu that changes daily or weekly, so its page leads with the menu for a date; a Café sells a menu that rarely changes, so people look at what's there and what it costs; a Bar is a café for drinks. A University café whose main offer is a hot menu that changes (Scholars Brew, Ground Café, …) is Dining, and keeps its café hours. A café that becomes a bar in the evening, in the same room, is one venue: `type` is its icon, and its café (`snacks`) and bar hours also list it under Cafés and Bars (`venueTypes()`), in filters, search and coverage. Formal hall is the `formal` meal: a slot on the dining venue whose room it's held in, or, where it has a room of its own (St John's, Christ's, Clare, Jesus, Magdalene, Pembroke and Robinson's Hall or Dining Hall, Newnham's Clough Hall, Queens' Old Hall), a dining venue of its own. It's booked ahead, so it only counts towards "open now" when Formal is the meal picked or it's all the venue holds; a `formals` row (`Venue.formal` in the app) lists a place under Formal even when its days aren't published.

## Deploy

Static `dist/`, every page prerendered: `/jesus/caff` is `jesus/caff.html`, plus `sitemap.xml`, `llms.txt`, `llms-full.txt`, `robots.txt` and `404.html` (no SPA fallback: a missing page is a real 404). Prerendered pages leave out anything that depends on the clock (`snapshot`). Canonical origin `SITE_URL` in `src/lib/site.ts`.

Cloudflare Pages: build `npm run build`, output `dist`, env `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, and `VITE_PHOTOS_URL` once photos are served. Pages are as fresh as the last build: create a deploy hook (Settings → Builds → Deploy hooks) and save it as the repo secret `CF_PAGES_DEPLOY_HOOK` so each ingest run rebuilds. A venue added in the dashboard 404s until the next build.

## Photos

Venue photos (`kind` venue) are shown at the top of the venue page and the map card, and as each venue page's `og:image`; photos of menu boards (`kind` menu) are kept as the source of a transcription and not shown. Files live in a Cloudflare R2 bucket, public at `VITE_PHOTOS_URL`, as `<site>/<venue>/<id>-<width>.webp` (480/960/1600 px, never wider than the original, metadata stripped, upright); `venue_photos` (`0018`) holds each one's path, widths, size, dominant colour (shown while it loads), alt text, credit and licence, and only approved rows are public. `npm run ingest:photo` makes the sizes, uploads them and adds the row as approved, so run it only for photos that are ours or a contributor's with a licence, with no recognisable people. Not from Google Maps or social media: their photos belong to the people who posted them, and Google Maps Platform's terms forbid taking its content out. Needs `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` in `.env`. Without `VITE_PHOTOS_URL` the app shows no photos.

## Page alignment

`Container` gives the header, main content and footer the same `max-w-7xl` edges. The directory and coverage tiles expand into columns; prose, hours and menu details keep readable inner widths aligned to the left edge.

## Map

Use verified venue or containing-building coordinates, never a college/site centroid or an invented room location. Unmapped venues stay in the List and the directory. Location sources are recorded in Supabase; `0012`/`0013` seed points from the University map; `0015` adds college venues whose OpenStreetMap point falls inside a University-map building of that college (the building's centroid is stored), or whose building a college source names; `0019` finishes the list the same way (every venue now has a point and a `location_source`), falling back to the OpenStreetMap building outline when the University map lacks the building (Lucy Cavendish's New Building). To place a new venue: find the building a college page names, `pip` it against the `UoCUniMapBuildingsGroup_View` layer (point-in-polygon query, `geometry=lon,lat&spatialRel=esriSpatialRelIntersects`), store that building's `latitude/longitude` and its `objectIds=` query URL. `src/components/VenueMap.tsx` dynamically imports MapLibre GL (SSR-safe, Vite worker bundled locally) and never groups places: one marker each, with places sharing a coordinate set side by side (`sideBySide()` in `src/lib/map.ts`). Pins are dots, no icons, in their type's colour from the Cambridge palette (Dining Dark Crest, Café Indigo, Bar Dark Cherry; tokens `--type-*` in `index.css`, validated as categorical colours on both basemaps), with a white halo: a ring when not open, filled when open now; selection is larger, Cambridge Blue on Dark Blue. The key in the map's corner names the type colours and open/not open; the type chips above carry the same colours with the type icons. It uses OpenFreeMap Bright (light) / Fiord (dark) vector tiles with visible attribution. Styles follow both the theme toggle and system appearance without resetting the camera or selection. Optional `VITE_MAP_LIGHT_STYLE_URL` / `VITE_MAP_DARK_STYLE_URL` override each theme; `VITE_MAP_STYLE_URL` overrides both. On mobile the map fills the viewport below the header edge to edge, with search and filters overlaid; desktop keeps the shared page width and a rounded frame, as tall as the screen allows (`--map-top`, measured by Explore). Wheel/trackpad scrolling and mobile pinch act directly on the map, with rotation disabled; `src/lib/mapGestures.ts` handles desktop Safari GestureEvents on the map canvas only. Page gestures outside the map and keyboard browser zoom are untouched. Default view centres on Cambridge; Show all fits matching points. Zooming out stops at `REACH` in `VenueMap.tsx` (Dry Drayton to Teversham, Histon to Trumpington): the minimum zoom is whatever fits that box at the map's current size, so a phone still sees it all across. Opening status is live, while menu date stays explicit.
