# Grub (grub.cam) — agent notes

Cambridge college and University menus and hours, live. Vite + React 19 + TypeScript + Tailwind 4 SPA reading Supabase (Postgres). **The database is the system of record**: sites, venues, hours and menus live there, not in the repo. A site is a college or a University site (West Cambridge, Sidgwick, a museum, …); a venue belongs to one. Those are the only two words for them, in copy, code and URLs: never "place". The repo holds code, migrations, and how each venue publishes its menu.

## Commands

| Command | What |
|---|---|
| `npm run dev` | Vite dev server (needs `VITE_SUPABASE_*` in `.env`) |
| `npm run ingest -- [--only jesus,homerton] [--from 2026-09-28] [--dry]` | Copy every source's channel to `venues`, then fetch every scripted source from this week's Monday (or `--from`'s week, to fill in the past: Jesus, Corpus, Selwyn and Robinson keep years of days) until a week ahead comes back empty → Supabase |
| `npm run ingest:manual -- menu.txt [...] [--dry]` | Save hand-transcribed menus → Supabase (format at the top of `scripts/ingest/manual.ts`) |
| `npm run ingest:prices -- prices.txt [...] [--dry]` | Save a venue's posted price list → Supabase, replacing the last one (format at the top of `scripts/ingest/prices.ts`) |
| `npm run ingest:photo -- <site>/<venue> <photo.jpg \| Commons file> --alt "…" [--credit …] [--kind menu] [--dry]` or `-- --list file` | Make a photo's sizes into `public/photos` and add it to Supabase, credited from Commons (see Photos) |
| `npm run ingest:hours -- hours.txt [...] [--dry] [--keep]` | Save a venue's opening hours → `service_slots`, replacing its slots unless `--keep` (format at the top of `scripts/ingest/hours.ts`) |
| `npm run submissions -- list \| show <id> \| transcribe <id> file.txt \| approve <id> \| approve --trusted \| reject <id> "why"` | The queue of what people sent in from `/send` (see Submissions) |
| `npm run models:compare -- <dir> --model a=in/out [...]` | Which OpenAI model transcribes boards best: each model on each photo in `<dir>` against its hand-checked `.txt`, scored per line, with cost (format at the top of `scripts/ingest/compare-models.ts`) |
| `npm run submissions -- digest` | What waits for you, as Markdown (no personal data): the queue Action (`.github/workflows/queue.yml`, 07:00 and 18:00 UTC) keeps it as the body of the open "Review queue" issue, commenting when it changes so GitHub emails you |
| `npm run reviews -- list [--all] \| approve <id> \| hide <id> "why"` | Members' reviews held back by the check (their words and author, for you alone), or all of them; publish one, or take one down for good |
| `npm test` | Vitest (time logic, filters, search against a real-data snapshot, SEO output, adapters against saved pages) |
| `npm run search:snapshot` | Save what the app loads today to `src/lib/fixtures/snapshot.json` for the search tests (then re-check their dish examples) |
| `npm run typecheck` / `npm run lint` | `tsc -b` + scripts tsconfig / oxlint |
| `npm run build` | typecheck + Vite build + `scripts/prerender.ts` → `dist/` (needs `VITE_SUPABASE_*`: pages are rendered from live data) |

`--dry` fetches and validates without writing. If ingest gets "fetch failed" for Magdalene locally, run with `NODE_USE_SYSTEM_CA=0` (keychain cross-signed certs break that chain).

## Layout

- `scripts/ingest/sources.ts` — **how each venue publishes its menu**: one entry per venue (`venues.id` = `<site>/<venue>`), channel (html/json/pdf/sway/canva/app/email/intranet/none), URL, cadence, notes, and an `adapter` for the 15 scripted ones (`scripts/ingest/sources/*.ts`: 11 colleges, Magdalene's Formal Hall from the same viewthe.menu page as Ramsay Hall, plus `ucs.ts` for the three University Catering pages with a weekly menu), and `weeksAhead` where a source publishes further than a Full Term at once (Peterhouse). Adapters must take dates from the source, never from the requested week, and only emit a meal the source has dishes for (Peterhouse lists the salad bar and desserts every day; Sunday has no lunch); tests run them on saved pages in `sources/fixtures/`. Each run copies channel, URL and scripted-or-not to `venues.menu_channel/menu_url/menu_scripted` (`0007`), for `/coverage`; edit them in `sources.ts`, not the dashboard.
- `scripts/schema.ts` — zod for `Dish` / `MenuDay`, checked before anything is saved; the app imports the types.
- `supabase/migrations/` — tables + RLS (anon SELECT only). `sites` (`kind` college | university) → `venues` (`url` = the venue's own page; who can eat there and how to pay were dropped in `0027`, since the member/guest and card rules are much the same at every college) → `service_slots` (meals: breakfast, brunch, lunch, dinner, formal, snacks = café, bar) and `formals` (booking, dress, guests, price notes; one per venue that holds formal hall); `0004` seeded the University venues once, `0009` reviewed the whole list, `0014` checked the University ones against catering.admin.cam.ac.uk/cafes. Menus: `menu_days` (one per venue/date/service, upserted) → `menu_items` (dishes as printed, replaced per day) → `dishes` (one per site + `dish_key(name)`, tracked across weeks); `dish_stats` view; `ingest_runs` (one row per source per run; service role only). Price lists as posted: `venue_prices` (`0008`, `0011`, `0017`, `0020`, `0021`; a first and a second price, replaced per venue; a line can be a range ("£3.24–£3.96", `price_max_gbp`), or priced for the second tier only; a line can price a course or the whole meal at some meals, else it's an item sold at them; diet `tags` from the codes printed after a name). Dishes can carry a second price too (`menu_items.price2_gbp`: Robinson's non-member, Wolfson's others'). Whose the two prices are and how a venue's pricing works is the venue's own convention, kept in `venues.price_terms` (`0020`, edited in the dashboard): `tiers`, the price columns' headings in its order (Members/Non-members, Senior/Student, Students and staff), and `note`, its rule for anyone else in words (St Catharine's: VAT on top, a further 35% for external customers; Wolfson: students 25% off), shown under its menu and list. Never compute a price from a percentage: say the rule. `formals` (`0017`): the fields the page shows (`gowns`, `dress_code`, `guests_allowed`/`guests_max`, `book_via`, `book_days_before` + `book_by`, `url`, `price_gbp`/`guest_gbp`/`prices_seen`, `days` when there's no slot), filled only where the notes say it plainly; the other text columns are notes. `photos` (`0018`, `0025`, see Photos). Writes go through `save_menu()` / `save_prices()` (service role only). Moving a venue to a new id moves its slots, menus, ingest runs, prices, formals and photos.
- `src/lib/data.tsx` — `load()`s sites/venues/slots and the next 7 days of menus (`main.tsx` renders once it has, keeping the prerendered HTML up until then); `useMenuDates`/`useMenuOn` fetch a venue's full menu history (past and future) on demand. `src/lib/time/*` — Europe/London clock, Full Term dates, `openStatus()`; `src/lib/filters.ts` — ranking and sections (Open now / Later today / Other days / Hours not published). `src/lib/seo.ts` — per-page descriptions and schema.org data, sitemap, llms.txt.
- `src/pages/*` — the venue is the unit, and there are few pages. `/` the front page and the one place to find somewhere (`Home.tsx`, decided Oct 2026: Explore and the Directory had become the same list and were folded into it): a tab per kind of venue, each its own address (`/` All, `/dining`, `/cafes`, `/bars`, `/formal`; `SCOPES` in `src/lib/finder.ts`), its heading saying what the site is for that kind ("Cambridge University food and drink", "…dining", "…cafés", "…bars", "…formal halls") over its list, as Airbnb's "Over 1,000 homes"; the tabs and one search (it filters as you type) are in the header; then that tab's venues beside the map, with its filters (Open now, Nearest first, Colleges and sites; Dining also its date within the loaded menu week, meal and diet, as chips that are selects, `ChipSelect`). ## Menus

Search (`src/lib/search.ts`, indexed once per loaded snapshot) follows Meilisearch/Typesense/Algolia rather than inventing rules. One document per venue and per dish on a day's menu; a dish carries its venue's names. Fields, best first: venue name (plus "<site> College"), alias, venue type and meals (`dining`/`cafe`/`bar`, `lunch`…), dish name, diet tags and service. Query words match exactly, as English plurals or `SYNONYMS` (spelling variants seen on menus), the last one also as a prefix unless followed by a space; one word written as two or two as one ("stjohns", "dar bar"); stopwords dropped. Typos (Damerau: 1 from 4 letters, 2 from 8, a wrong first letter costs 2) only for a word that matches nothing as typed, so real words never drift ("cake" ≠ "hake"). Words are optional: results are what matches the most of them. Ranking is tie-breaks: typos, worst field, the query naming the whole venue or dish, exact words, then open status. Search sees only what the filters leave: dishes on the selected date (today on Home, never silently tomorrow; browsing still previews the next service), at the selected meal, carrying every selected diet tag. Results bypass opening-status groups. Nicknames are data, not code: `sites.aliases` / `venues.aliases` (`0005`, `0006`), edited in the dashboard. `src/lib/search.test.ts` runs judged queries against a real snapshot (`npm run search:snapshot`) plus rules on made-up data; add a failing query there before changing the rules.

No projected menus: only what a source has published is saved, and sources are re-checked often instead (GitHub Actions runs `npm run ingest` every two hours from 04:37 to 18:37 UTC: GitHub delays or drops runs at busy minutes, and with three a day nothing ran before 11:10 UTC; needs repo secrets `VITE_SUPABASE_URL` and `SUPABASE_SECRET_KEY`, then rebuilds the site through `CF_DEPLOY_HOOK` when that's set). Days already saved are kept; a day the source still lists is replaced with the latest version. Menus are filed under the meal the venue serves that day when the source names one it doesn't but its brunch counterpart is (Corpus posts Saturday's brunch as "Lunch"): `servedService()` in `src/lib/time/openNow.ts`, applied as menus load.

Hand-transcribed venues (see `sources.ts`): open the URL (PDFs: `curl -A "Mozilla/5.0" … | pdftotext -layout - -`; Sway/Canva: `"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless=new --dump-dom URL`), write a `.txt` outside the repo (`~/grub-data/menus/`), `npm run ingest:manual -- file.txt`. Diet codes in brackets after a dish become tags, so write them as the college means them: Lucy Cavendish's legend is V = vegan, Vn = vegetarian (the reverse of the usual), write "(vegan)"/"(vegetarian)"; Clare Hall's PB is plant-based. St Catharine's prints its whole 4-week cycle with every week's dates on each PDF, so one pass fills the term; Fitzwilliam and Lucy Cavendish print formal menus too (`formal` on the venue that holds them). Canva's rendered DOM only shows the first page; later pages are in its JSON (`"A":["…"]` text runs, each supper block listed just before its day's label). Queens' page sits behind a BotDetect CAPTCHA, even for headless Chrome. Members-only colleges need a collaborator; their photos of noticeboards and price lists go in the same way (menus via `ingest:manual`, prices via `ingest:prices`).

Reference data (hours, venues) is edited in the Supabase dashboard until there's an editor UI. Unknown hours ⇒ no slot (UI says "Hours not published", never "closed").

A venue is somewhere you go to eat or drink (`0009`): not common rooms, tea or coffee gatherings, vending machines or overflow seating. Its `type` is what people come to it for (`0017`): Dining (`hall`) serves meals from a menu that changes daily or weekly, so its page leads with the menu for a date; a Café sells a menu that rarely changes, so people look at what's there and what it costs; a Bar is a café for drinks. A University café whose main offer is a hot menu that changes (Scholars Brew, Ground Café, …) is Dining, and keeps its café hours. A café that becomes a bar in the evening, in the same room, is one venue: `type` is its icon, and its café (`snacks`) and bar hours also list it under Cafés and Bars (`venueTypes()`), in filters, search and coverage. Formal hall is the `formal` meal: a slot on the dining venue whose room it's held in, or, where it has a room of its own (St John's, Christ's, Clare, Jesus, Magdalene, Pembroke and Robinson's Hall or Dining Hall, Newnham's Clough Hall, Queens' Old Hall), a dining venue of its own. It's booked ahead, so it only counts towards "open now" when Formal is the meal picked or it's all the venue holds; a `formals` row (`Venue.formal` in the app) lists a venue under Formal even when its days aren't published.

## Deploy

Static `dist/`, every page prerendered: `/jesus/caff` is `jesus/caff.html`, plus `sitemap.xml`, `llms.txt`, `llms-full.txt`, `robots.txt` and `404.html` (no SPA fallback: a missing page is a real 404). Prerendered pages leave out anything that depends on the clock (`snapshot`). Canonical origin `SITE_URL` in `src/lib/site.ts`.

Cloudflare Workers with static assets (`wrangler.jsonc`: no script, `dist` served as files, `404.html` for anything missing, `_headers`/`_redirects` as on Pages), the Worker `grub-cam` connected to the repo through Workers Builds: every push to `main` runs `npm run build` then `npx wrangler deploy`. Build variables (Settings → Build → Variables and secrets, not the runtime ones): `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_MAPKIT_TOKEN`. grub.cam's DNS is on Cloudflare (registrar Porkbun), the domain attached as the Worker's custom domain, www redirected to it. Pages are as fresh as the last build: a deploy hook (Settings → Builds → Deploy Hooks) saved as the repo secret `CF_DEPLOY_HOOK` makes each ingest run rebuild. A venue added in the dashboard 404s until the next build.

## Submissions

How information gets in. **Scripted, recurring**: `sources.ts` adapters, run by the ingest Action every two hours, and members' photos of a venue (below), the only automated paths. **By hand**: `ingest:manual`, `ingest:prices`, `ingest:hours`, `ingest:photo`, and SQL migrations for reference data, each with its source. **Sent in**: `/send?venue=<id>&kind=menu|prices|hours|photo|other` (`src/pages/Send.tsx`), linked from every gap on a venue page ("Send a photo of the board / the list / the times", "Send one", "Report a change"), the footer and Coverage. The sender signs in with a Cambridge account (Microsoft through Supabase Auth, `src/lib/auth.ts`, a second client that keeps its session; see Accounts), adds a photo (shrunk to 1600 px in the browser, `src/lib/submit.ts`) and/or text; the `submit` Edge Function checks the bearer token is a user's with an @cam.ac.uk address (contributors' token posts excepted), (`supabase/functions/submit`) stores the photo in the private `submissions` bucket, inserts a `submissions` row (`0024`; `user_id`/`user_email`, `0026`), and has OpenAI transcribe it into the kind's ingest text format, through the Responses API with the answer in a fixed shape (`supabase/functions/_shared/openai.ts`: the body, whether anything was readable, and what it was `unsure` of, shown to the sender and in `submissions show`); OpenAI only (Gemini dropped Oct 2026). Secrets: `OPENAI_API_KEY`, `OPENAI_MODEL` (default `gpt-5.4-mini`), `OPENAI_PRICE` (its dollars per million input/output tokens, "0.75/4.50"), optionally `OPENAI_REASONING` (effort for a reasoning model) and `LLM_DAILY_USD` (default 2). Every call is logged in `model_calls` (`0029`: purpose, model, tokens, cost) and none is made once the day's calls have cost `LLM_DAILY_USD`, so a burst can't spend the credit. Pick the model with `npm run models:compare -- <dir> --model a=in/out --model b=in/out` (photos of boards beside hand-checked transcriptions, scored per line, with cost and time; see the top of `scripts/ingest/compare-models.ts`). Secrets via `supabase secrets set`, deploy via `supabase functions deploy submit`. The sender sees that text, fixes it, and confirms (`action: confirm`), which queues it as `needs_review`; with no model available it waits as `received`. **Nothing is published by the function.** Except, one step removed, a member's menu: once its sender confirms the text, it's `queued` unless a script fetches the venue's menu or they've had 6 published in a day (`menuCanGoUp()`), and the photos Action (now Members' photos and menus) runs `submissions -- menus`, which publishes it when it parses, is for its venue and is dated yesterday to a week ahead (`menuHold()`), else sends it to `needs_review` saying why; `submissions -- reject <id>` takes a published one's days down again (only the member's: a script's or hand-copied menu for the same day stays). And a member's photo of the venue (`kind=photo`, "Have a better photo? Send it", a pill in the top corner of every venue's banner, `0028`): the function credits it to the account's Microsoft name (`full_name`, `memberName()` in `src/lib/auth.ts`), has the model check it (`vet()`: a real photo of the venue, no recognisable face, nothing unsuitable) and write its alt text; one that passes, while the sender has had fewer than 3 go up that day and no other member's photo of that venue went up that day, is `queued`, and the function starts `.github/workflows/photos.yml` (`GITHUB_DISPATCH_TOKEN`, a fine-grained token with Actions read and write on the repo; it also runs hourly), whose `npm run submissions -- photos` makes the sizes, adds the row ahead of the venue's others (`photos.submission_id`, licence CC BY 4.0, which the form grants), then commits `public/photos` to main, which deploys; one that doesn't pass, or arrives with no model available, waits as `needs_review` with the reason, and `approve <id>` publishes it the same way. `reject <id>` takes a published one down (unapproves its row) and the photo before it shows again. `npm run submissions -- list / show <id>` (saves the photo under `~/grub-data/submissions/` and prints the prompt from `supabase/functions/_shared/formats.ts`, to paste into any chat model when the APIs aren't available) `/ transcribe <id> file.txt / approve <id> / reject <id>`: approve parses the text with `parseManual`/`parsePrices`/`parseHours` and saves it through the same calls as the hand scripts (`method` `user`), replacing the venue's hours (`--keep-hours` adds) and price list, upserting menu days; slots carry `prov.submission`. **Contributors** (`contributors`, a sha256 token hash and optionally the sites they may post for) post JSON with `X-Contributor-Token` and their own transcription from a script that can reach a members-only source; their rows are `needs_review` and the Action's `approve --trusted` publishes them (`method` `contributor`). Mint a token: any 32 random bytes hex, store `encode(sha256(token), 'hex')` in the dashboard, hand over the token. Rate limit: 12 an hour per hashed address; a honeypot field; 5 MB photos. `CONTRIBUTING.md` says this to people. Photos of boards and lists are evidence for the transcription, not shown.

## Reviews

A signed-in Cambridge member rates a venue 1–5, with up to 1,000 characters if they like (`reviews`, `0030`): one per member per venue, changed or taken back from the venue's page. Written only through the `submit` function (`action: review`): a rating alone is published; words go through OpenAI's moderation (free) and then `OPENAI_REVIEW_MODEL` (default `gpt-5.4-nano`; `OPENAI_REVIEW_PRICE`) asking whether they're about the venue and name or attack no one, published when both pass, else `needs_review` with why (and when no model can look). One a person hid stays hidden whatever its author does. Shown anonymously ("Cambridge member", the month), and only once a venue has 5 published: the public views `venue_ratings` (count, average) and `venue_reviews` (no author) hold nothing for a venue with fewer, so the threshold can't be read around; a member reads their own through RLS. Held back: `npm run reviews`, and the Review queue issue lists them (stars and why, never the words). 20 writes a member a day.

## Photos

Every venue has a picture: its photo (`kind` venue, the first by `position`), or its type's tile until it has one or if the photo can't load (the type's tint with its icon in the middle; `VenueImage` in `components/VenuePhoto.tsx`). Every site has one too (`SiteThumb`: its photo, else a plain tile with a mortarboard or a building), in the directory, the credits and as its page's `og:image`; `scripts/ingest/photos-sites-commons.txt` lists them, mostly the lead image of the site's Wikipedia article. It's the venue page's banner, the top of its map panel, its square in lists (with the type's mark in the corner) and its page's `og:image`. Photos of menu boards (`kind` menu) are kept as the source of a transcription and not shown. Each photo is credited where it's shown (author, licence linked to its deed, its Commons page) and all of them on `/credits`.

Files live in the repo, `public/photos/<site>/<venue>/<id>-<width>.webp` (240/480/960/1600 px, never wider than the original, metadata stripped, upright), served by the site itself and cached for good (`public/_headers`; a path is never reused); `VITE_PHOTOS_URL` can move them to a bucket later without touching the database. Not Supabase Storage: its free egress is shared with the database. `photos` (`0018` as `venue_photos`, `0025` for sites: the subject is `venue_id` or `site`, a site's path is `<site>/<id>`) holds each one's path, widths, size, average colour (shown while it loads), alt text, credit, licence and source, and only approved rows are public.

`npm run ingest:photo -- <site>/<venue> <photo.jpg | Commons file> --alt "…"` (or `<site>` alone for the site's own photo) makes the sizes, writes them to `public/photos` and adds the row as approved; commit the files (the site shows the tile until they're deployed). For a Wikimedia Commons file (its page URL or `File:Name.jpg`) the author, licence and page are read from Commons, and anything that isn't CC0, public domain, CC BY or CC BY-SA is refused. `--list file` takes one per line (`scripts/ingest/photos-commons.txt`: every venue's photo from Commons, with what it shows; run again, it skips what's saved). Whose photos: ours, a contributor's with a licence, or openly licensed on Commons (Geograph's are there too), never with recognisable people. Where no free photo of the room exists, the building or court it's in, and the alt text says so. Never from Google Maps, social media or a college's own site: those belong to whoever took them, and Google Maps Platform's terms forbid taking its content out. 39 venues have no free photo yet (mostly in-college bars and cafés, and newer buildings).

## Page alignment

`Container` gives the header and footer the same edges on every page (decided Oct 2026, so the header never moves): the whole window, as Airbnb's, 16/24/48px gutters, up to 1920px (`max-w-[120rem]`). The front page's tabs use those edges too: the list beside the map (`.finder`) runs from the header to the footer and sets its own space (`main:has(.finder)`). Every other page reads in a centred column 76rem wide inside them, a 22rem rail beside the main column on venue and site pages (`Layout` in `App.tsx`, decided Oct 2026 after Luma's and Airbnb's listing pages), its banner across it. Lists are always one column (the front page's venues, a site's venues, the credits), a map beside them on a wide screen; only the coverage tiles and a day's meals sit side by side. Prose, hours and menu details keep readable inner widths aligned to the column's left edge.

## Map

Use verified venue or containing-building coordinates, never a college/site centroid or an invented room location. Unmapped venues stay in the List and the directory. Location sources are recorded in Supabase; `0012`/`0013` seed points from the University map; `0015` adds college venues whose OpenStreetMap point falls inside a University-map building of that college (the building's centroid is stored), or whose building a college source names; `0019` finishes the list the same way (every venue now has a point and a `location_source`), falling back to the OpenStreetMap building outline when the University map lacks the building (Lucy Cavendish's New Building). To locate a new venue: find the building a college page names, `pip` it against the `UoCUniMapBuildingsGroup_View` layer (point-in-polygon query, `geometry=lon,lat&spatialRel=esriSpatialRelIntersects`), store that building's `latitude/longitude` and its `objectIds=` query URL. Maps are Apple's (MapKit JS, `src/components/AppleMap.tsx`: its full Standard style, light or dark with the theme, none of its own places, so nothing competes with the pins) when `VITE_MAPKIT_TOKEN` is set (a MapKit JS token made in the Apple Developer account, Services → Maps → Configure → Tokens, restricted to grub.cam's domains, no expiry; Apple makes one per domain, so `VITE_MAPKIT_TOKEN` lists them comma-separated and a page picks its own domain's (`pickToken()` in `lib/mapView.ts`); in `.env` and the host's build env. Apple matches the domain exactly, so it's refused on localhost: `npm run dev` uses a second, unrestricted token from `.env.development.local`), else, or once Apple's fails to load or refuses the token, OpenFreeMap's through MapLibre GL (`OpenMap` in `VenueMap.tsx`), so forks and builds without the token still have a map. Both share props, pins and framing (`components/MapParts.tsx`, `lib/mapView.ts`). `src/components/VenueMap.tsx` dynamically imports MapLibre GL (SSR-safe, Vite worker bundled locally), MapKit JS loads from Apple's CDN only where a map shows, and neither groups venues: one marker each, with venues sharing a point, or within 8 m of one another, set side by side (`sideBySide()` in `src/lib/map.ts`: a pair in a row, three as a triangle so each keeps room for its name, more as a grid); a pin hangs from a point of no size (`.venue-pin-origin`), as MapKit places an annotation by the size it reads when it first shows it, which varies with what has rendered (pins drifted when they came back into view). Pins are drawn as Apple marks its own places: a 24px disc in their type's colour from the Cambridge palette's vivid secondaries (Dining Crest, Café Green, Bar Indigo; tokens `--type-*` in `index.css`, decided Oct 2026 for being vivid on both basemaps; they differ in hue more than lightness, so the glyph always repeats the type), lit from above (`--sheen`, a gradient laid over the fill), with the type's glyph in white, a white rim and a soft shadow, split diagonally between two colours for a venue that's two kinds (a café that's a bar by night: `pinFill()`); open or not, every pin looks the same, the list says what's open; selection is larger, ringed in Dark Blue (Cambridge Blue on the dark basemap). From zoom 15 (`LABEL_ZOOM`), and for the picked pin always, each pin has its name beside it in a darker shade of its colour, haloed, as Apple's labels (`pinLabel()`: the college first where the name alone says nothing, "Pembroke · Hall"), placed right else left where it overlaps no pin or name and dropped otherwise (`placeLabels()`/`labelPins()` in `lib/mapView.ts`, rerun when the map stops moving or its pins change, then each frame until the pins are drawn where they were projected and the names have widths, since MapKit reports a move, or adds a pin, a moment before drawing it: `labelUntilMeasured()`). Apple's map uses its full `Standard` style with every one of its places filtered out (`PointOfInterestFilter.excludingAllCategories`: the runtime name, not the typings' `filterExcludingAllCategories`): their icons and names, parks and stations too, competed with the pins and theirs. You are here is a dot hung from a point of no size, as a pin is (`userDot()`). The type badges and tiles in the list carry the same colours with the type icons. It uses OpenFreeMap Bright (light) / Fiord (dark) vector tiles with visible attribution. Styles follow both the theme toggle and system appearance without resetting the camera or selection. Optional `VITE_MAP_LIGHT_STYLE_URL` / `VITE_MAP_DARK_STYLE_URL` override each theme; `VITE_MAP_STYLE_URL` overrides both. On a phone the front page's map fills the screen, edge to edge, its zoom buttons hidden (pinch); on a wider screen it sits beside the list in a rounded frame, sticky, as tall as the screen allows below the header. Wheel/trackpad scrolling and mobile pinch act directly on the map, with rotation disabled; `src/lib/mapGestures.ts` handles desktop Safari GestureEvents on the map canvas only. Page gestures outside the map and keyboard browser zoom are untouched. Default view centres on Cambridge; On the front page Nearest first puts you on the map too; a map with nothing else on the page keeps its own Near me and Show all (`controls`). Zooming out stops at `REACH` in `lib/mapView.ts` (the venues and about 600 m round them: Madingley Hall to the Biomedical Campus, Girton to Addenbrooke's; widen it for a venue further out): the minimum zoom is whatever fits that box at the map's current size, so a phone still sees it all across (MapKit limits the camera's height instead, so `AppleMap` works out the height that fits `REACH` from what the map shows now, again on resize), and Apple's map keeps its middle inside it. Opening status is live, while menu date stays explicit.
